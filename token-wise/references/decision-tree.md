# 分级闸门决策树

> 用途：agent 在每轮执行时，根据任务类型与上下文状态判定当前任务允许使用的省 token 手段级别。
> 判定顺序：先查保护名单 → 再查上下文占比 → 最后落到 L 级别。
> 注意：所有判定在"宿主能力检测"之后进行——能拿 usage/cache 数据用实际值，否则用估算值并标注。

## 一、上下文占比分级（替代写死的 token 阈值）

```
context_ratio = 当前上下文估算 / 模型 context window
（宿主暴露 usage → 用实际值；否则按轮数×平均轮 token 粗估，标注"估算"）

  < 30%    正常 —— 不干预
  30~50%   观察 —— 留意历史增长，不主动动作
  50~70%   提醒 —— 建议 /compact 或精简历史（L1 摘要）
  70~85%   强提醒 —— 强烈建议整理；或结束当前上下文、带小结新开
  > 85%    建议结束 —— 继续 = 高成本 + 注意力分散（L2 或新会话）
```

综合信号判断（不只 token 数）：context size + utilization + task state + cache status + correction count。
**缓存过期 ≠ 上下文丢失**：TTL 失效只影响计费折扣，不影响继续对话。

## 二、任务分级

```
任务开始
  │
  ├─ 命中 protected_tasks？──────────────► 仅 L0 + L1(仅输出压缩) + 强制规划(R4) ──► 执行
  │
  ├─ 简单机械类（工具函数/重命名/查文档/简单配置）？
  │     ├─ conservative ────────────────► L0
  │     ├─ balanced    ────────────────► L0 + L1
  │     └─ aggressive  ────────────────► L0 + L1 + L2(允许 compact/降档)
  │
  ├─ 常规开发（业务代码/小功能/修已知 bug）？
  │     ├─ conservative ────────────────► L0
  │     ├─ balanced    ────────────────► L0 + L1
  │     └─ aggressive  ────────────────► L0 + L1（L2 需显式命令）
  │
  └─ 复杂推理类（架构/重构/疑难 bug）？──► 强制 L0 + 规划模式（R4）
        且禁用：L2 全禁；L1 仅输出压缩；thinking 不许降档
```

## 三、L 级别定义（L0 Context / L1 Output / L2 Reasoning-Model）

| 级别 | 定位 | 手段 | 副作用 |
|---|---|---|---|
| L0 Context 优化 | 减少垃圾 | 删冗余、精确搜索（precise_ref auto）、按需读取、避免重复解释、subagent 隔离、缓存友好排序 | 无，永远安全 |
| L1 Output 优化 | 减少表达 | 输出压缩（禁寒暄/diff 优先/默认简版）、summary 型历史管理、/clear 建议 | 教学与解释场景信息密度下降，需豁免；diff-only 非无损，复杂修改要补影响范围/风险/测试 |
| L2 Reasoning/Model 优化 | 动模型能力 | /compact 全量压缩、模型降档（router 推荐）、降低/关闭思考 | 丢失推理链与细节，易前后矛盾，禁止用于受保护任务 |

**两个边界修正（评审确认）**：
- subagent 隔离 = 减少上下文污染（L0），**不保证省 token**（subagent 自身消耗 token）。
- diff-only = 输出压缩（L1），**不是无损**；用户要解释时恢复详细输出。

## 四、自动进保护名单的信号

1. 同一问题被修正 ≥2 次（失败尝试已污染上下文 → 建议整理/重开，而非压缩）。
2. 用户明确说"解释给我听 / 讲清楚为什么"（teaching 语义）。
3. 任务涉及支付、鉴权、权限、密钥、数据库迁移、生产故障等敏感场景。
4. 用户显式说"这个别省" / "保证质量优先"。

## 五、路由与思考的配合

1. `router` 是**策略层**：agent 按任务分类推荐 light/heavy 模型；实际切换由宿主执行；宿主不支持时提示用户手动切。
2. 复杂任务强制 thinking 最大档；只有 `protected_tasks` 之外且用户显式要求才允许降档。
3. 路由误判的代价 = 复杂任务交给弱模型 → 必返工 → 总成本更高。拿不准按"复杂"处理。

## 六、效果评估挂钩

- 每个任务记录：task / model / input / output / cache_hit(若有) / retry / correction / success。
- 收尾或 `/token-wise report` 时输出：估算成本、默认策略对比、节省比。
- 有数据才有结论：任何"省了多少"的宣称必须有统计支撑（详见 `evaluation.md`）。
